# Video pipeline

Two looks share this pipeline: **3Blue1Brown** (this file; the default, for codebases and mechanisms) and **纸面图解 paper style** (`video-paper.md`; for essays, research posts and handbooks, `new_episode.py --style paper`). Everything below about the pipeline, script.json, TTS, timing and slides applies to both; the sections on audience, the teaching pattern and the 3b1b look apply to the 3b1b style.

Folder: `episodes/epNN-<slug>/` (from `scripts/new_episode.py`). Needs `ffmpeg`, Node + `npm install` (playwright-core), Google Chrome (or `CHROME_PATH`), and `GEMINI_API_KEY` in `~/.config/course-studio/.env` (shared by every course; a course-root `.env` or the environment can override it). Never put the key in the skill, the repo or a committed file.

```
script.json ──tts.py──▶ audio/*.wav (cached) + narration.wav/.mp3 + timeline.json
            └─silent_timeline.py─▶ same outputs, silent audio, subtitle timing by reading speed (no key, no quota)
head.html + scenes.js + tail.html + timeline.json ──build.py──▶ index.html  (open to preview, scrub, play with audio)
index.html?record + narration.wav ──node record.mjs──▶ video.mp4 (1920×1080, 30fps, h264 + aac)
index.html?record&nosubs + timeline.json ──node slides.mjs──▶ slides/NNN.jpg + slides.json + slides.html + slides.pdf  (课件)
timeline.json ──site/dev/sync_content.py──▶ content/epNN/chapters.json
```

## Defaults: what every episode video is

- **Audience: engineers.** Every course made with this skill is for engineers who want to master a real codebase or system; their backgrounds vary. See "Who the videos are for" below.
- **Length: no cap — as long as the mechanism needs to be learned, and no padding.** What limits a video is *density*, not minutes: one mechanism and one running example per video. Whether a topic becomes one video or several parts (`11a`, `11b`, `11c` …, each with its own running example) is your call after reading its code. For reference, robot-course videos ran from 4 minutes (11d) to 19 (11b); most were 10–15. These numbers describe what was made; they are not targets. See "Hardcore and learnable" below.
- **Style: 3Blue1Brown** (below). The canvas palette in `head.html` is already dark with bright meaning-coded colours; use it.
- **Narration: English via Gemini TTS, bilingual subtitles.** Subtitles carry the Chinese, so one video serves both UI languages. A course may narrate in Chinese instead (`--narration zh`, English subtitles beneath); tts.py then voices the Chinese with MiniMax (see "tts.py").
- **Preview before narrating.** When the user wants to see the look first, or asks for no voice, run `silent_timeline.py` instead of `tts.py` and render; switch to `tts.py` later, everything else stays the same.

## Who the videos are for

| | |
|---|---|
| Who | engineers who want to master *this* codebase or system; some have deep backgrounds in its field, some shallow |
| Animation is for | showing what reading the code can't: timing (who interrupts whom, in what order), data flow across files, state machines side by side, model ↔ generated code, real waveforms before/after a change |
| Basics | set by the learners, recorded in the course plan: learners who know the field get one line at most; learners new to it get each prerequisite taught concept-first on first use (see "Concept first" below); either way an analogy wherever a fitting one exists (see "Analogies" below) |
| Code | the main subject, 40–50 %: real paths, function and variable names, cut lines marked `…`; a foundation episode that teaches the field (sglang-omni Part 0) may be mostly concept |
| Scene arc | problem (why it exists) → mechanism animation → source walkthrough → evidence (a real run, real numbers); a pitfall / design trade-off only when it makes the logic clearer (optional, see "Logic first, without jumps" below) |
| "Understandable" means | "so *that's* what this code does" — clear, not shallow |
| Voice (`tts.py`) | clear, confident senior engineer talking to a peer, brisk but unhurried |

Real evidence beats illustration: when the course has a runnable target (a simulator, the real tests), plot data from actual runs and quote measured numbers — and sample fast enough not to miss the transient you are describing.

## Hardcore and learnable (the default teaching pattern)

Depth is never cut; it is made followable. Learned on robot-course ep11: its first version, made before this pattern existed, put four encoder protocols, their checks and six pitfalls into one 10-minute video; it was correct but "too hard". the remake (ep11a: one protocol, one real frame followed end to end, 12 minutes) was understood on first viewing. It is how the 40–50 % code share gets absorbed.

- **Logic first, without jumps** (robot-course learners, 2026-11-04: not every lesson needs error handling; what they want is the framework's logic laid out clearly, with no jumps). The viewer always knows why we are at this line and how we got here.
  - **Narration order = run order** on the running example: the stops come in the order the code reaches them.
  - **Every stop is entered through what hands over to it**: the call, the interrupt, the function pointer, the queue, the flag. Never through "now let's look at X".
  - **Each scene ends on what it hands the next one** (the value, the flag, the call that comes next), and the next scene opens from it.
  - **Asides wait.** A variant, a what-if, a pitfall or a serving remark never breaks into the main path. It goes after the path reaches its output, or into another part.
  - **Error handling is optional.** A check on the path is read as code where it sits, in a line, with the running example passing through it ("the CRC matches, so it carries on"). A failure scene, a what-if or a pitfalls part is added only when it makes the logic clearer, never because the skeleton has a row for it.
- **Conclusion first, on one framework page** (robot-course learners, 2026-11-10: the code walk was fine, but after many episodes it "felt like reading code aloud, not laying out the logic"; complex episodes needed an AI or a second viewing; what they missed was summary and framework). Narration in run order delivers the episode's central idea last: over 47 robot-course episodes the first summary came at a median 55 % of the runtime (24a: minute 8.5 of 13.4), and the "journey" scene read out stop titles. A viewer who already holds the conclusion follows the walk; a first-time viewer has nothing to hang the details on. An AI asked about the episode gives exactly that missing layer, so the video gives it first.
  - **Right after the intro, say the whole mechanism in one or two plain sentences**, with no identifiers ("It keeps no plan. Every 100 µs it plans the whole trapezoid again from one position and one speed, then takes one step"). The sentence stays on screen as the page's heading.
  - **Then one framework page, in place of a table of contents**: one pass of the mechanism from top to bottom: what goes in, the steps in run order, every branch with its real condition (cut from the source with its line number, like any code on screen) and which ticks or cases of the running example took it, what comes out, what carries over to the next pass; beside it the real run marked with the same letters as the branches. Build it part by part as the narration names each part, then map the stops onto it ("eight stops follow tick 0 down this page, three go across ticks").
  - **The whole page is the overview, not the reading size.** In a frame that also holds the chapter title and two rows of subtitles, a page with everything on it has 12–14 px text; the user's first look at ep24a: "isn't this hard to read?". Keep the camera at about 1.5× on the part the narration is on (text 19–25 px, larger than the code panes), glide to the next part, and pull back to the whole page only to show its shape: once every part has been read, and when something spans the page (the loop back to the memory). The heading stays put; the board moves in a clipped window under it (ep24a `CAM` / `camPath`, `planPage({cam})`). Check a frame at the size of the site's player, not only at 1920.
  - **"So far" and the recap are told on that page**: the running example's path lit, each takeaway lighting the part it is about. Never text cards over an empty frame: the summary pages were the sparsest pages of the old videos.
  - **The stops stay as they are**: run order, verbatim code, the call chain. The page is the map they are walked on, not a replacement.
  - Numbers and line references on the page are checked like every other one (robot-course ep24a: `make_board.py` asserts each quoted line and counts the branch taken on every tick of the real run; `board.part.js` `planPage()` draws the page and takes `p` / `hot` to build it up and light parts; `framework/` renders the same data as a one-page still).
- **A picture where the logic is hard, a line where it is simple** (the same learners: pictures are not for quantity; a diagram on something simple "looks unnecessary and lowers the quality"). Draw branching, state carried from one pass to the next, timing, several cases side by side. Who calls it, plain inputs and plain outputs get one line or one row. A dense page is welcome (they asked for it: content spread thinly over many near-empty pages is harder to follow), as long as it is built up part by part and each spoken line still brings one new thing.
- **One running example, carried end to end.** Pick one concrete input from a real run (a frame `02 00 3C 99 00 A7`, a CAN write of 262144, a step of 0.1 N·m) and follow it through every stage until it becomes the output (178.71°). The same numbers appear in every scene. Never switch examples mid-episode except for a "what if it breaks" contrast, and say so.
- **A stop strip.** Number the stages when the framework page maps them (above) and keep a thin strip under the chapter title showing the current stop (ep11a `stopBar`, ep36 `routeBar`). The viewer always knows where they are.
- **One picture that ties the events together, across every part** (robot-course viewers, 2026-10-14, on the first ep06: by the later parts they had forgotten the earlier ones, the many key events did not connect, and the order was easy to get lost in). A stop strip only orders one video's stages; a topic with many events, or one split into parts, also needs a picture of *why* the events happen. Look for the few named conditions or states the events change (ep06's remake: four "gates", each one variable in the code, `bus_voltage_check_flag` … `hw_ready_state`, each opened by an event and each holding back a named function) and tell every event as a change on that picture ("gate 2 opens at 512.25 ms"), not as one more item on a timeline. Introduce the whole picture early, with what each element holds back; keep a small copy of it in a corner of every scene of every part, lit as events happen; open each part on it ("last time") and end each part with it updated; let the last part close with the whole topic on one page. Build it as one shared helper copied into each part (ep06a–e `gates.part.js`, `gateBoard()` / `corner()`).
- **Each step in three beats, same numbers:** (1) do it by hand on screen — the arithmetic written out (`02 ⊕ 3C = 3E`, `60 + 39168 = 39228`); (2) the real source, at most 3 lines lit at a time, the current value written beside each line (`codeBox` `mark`); (3) the real run printing the same value. Code never appears before the picture it implements, and the picture stays on screen while the code is read: picture on one side, code on the other, the lit line visibly tied to the part of the picture it changes (robot-course viewers asked for code, logic and diagram together, not in turns).
- **The narration says what the code does; line numbers stay on screen.** Spoken line numbers ("line 104 … line 110 … lines 115 to 124") crowd out the explanation and are forgotten at once. The gutter, the box title and the `mark` carry the location; the line itself says the role ("BspInit now starts the 1 ms timer and the ADC interrupt").
- **Code on screen is the real code, located and in call order** (robot-course ep11a learner: "代码不要简写，逻辑要连贯，看完知道代码在哪"). (1) Verbatim: the lines exactly as in the file — same identifiers (`enc_data->uart_handle`, not `uart`), same macros, same comments; never substitute values into the code, write them beside it (`mark`). Cut excerpts from the repo by line range at build time (like `lab_data.py`) so they can't drift. (2) Located: real line numbers in a gutter and `path/file.c · L615–628 · Function()` as the box title. (3) Continuous: walk the code in the order the CPU runs it — ISR → caller → function-pointer target → back to the caller → next call — with a call-stack breadcrumb on screen (`board.c:229 EncoderDataRead() › drv_encoder.c:202 .read › :615 TAMAGAWA_Encoder_Data_Read()`) that grows on each call and shrinks on return. Draw source in a font without ligatures (Menlo/Consolas): JetBrains Mono turns `->` and `!=` into → and ≠, which no longer matches the file. Never jump to a later function without showing the call that gets there; when lines inside a function are skipped, show an explicit `… L640–646: what they do` row instead of silently dropping them.
- **Say what you skip, and where it is taught** (robot-course, 2026-10-14). A video that keeps one mechanism will meet calls, branches and modes that belong to another episode (ep08's state machine calls `protect_check()`, which is ep21; its mode switch folds homing and CSP onto plain speed and position, which are ep25 and ep26). Never let them go by silently and never explain them in full: give one or two lines of what the thing does *for the running example* ("protect_check fills `error_code`; in this run it stays 0"), say that the details come in a later episode, and name that episode. On screen, a small bilingual tag on the skipped call or box: `→ 第 21 集 / ep21`. Keep the call chain intact around it (the call is still shown, in order; the skipped function is a box with its gloss, not a jump). Note each forward pointer in the course plan so the later episode picks it up ("ep08 promised: how `error_code` is set").
- **Every name the video points at says what it is** (robot-course viewers, 2026-10-14: some variables and functions went by with no explanation, so they lost track of what was being discussed; ep07b said `JDR1`, `bsp_get_phase_current` and `ERR_BIG_CURRENT` without one). Any identifier the narration says or a highlight lands on, whether a function, variable, struct field, macro, register, HAL call or error code, gets a short gloss of its *role*, not its name read back: "JDR1, the ADC register holding the latest injected conversion"; "bsp_get_phase_current, which turns the three ADC counts into amps". (1) Spoken the first time it comes up, in the same line or the next. (2) On screen while it is lit: a small bilingual tag beside the line or the name in the picture, so a viewer who missed the voice can still read it. (3) Said again in a few words when it comes back after other scenes, or in a later part of a split episode, since the viewer has forgotten it by then. Names that are on screen but never pointed at need no gloss. While writing `script.json`, look at each line that names code and ask whether a viewer who has never opened the file would know what that name is; the fact-check pass confirms each gloss against the source (a wrong gloss is worse than none).
- **Concept first, when the learners are new to the field** (sglang-omni, 2026-10-26). The first 0a–0c (8–11 min, ~105 wpm) were correct but the learner, a software engineer new to AI voice, needed an AI to follow parts of them. The pace was not the cause: the scripts gave vectors, distance, convolution and stride, embedding lookup, log-mel, dB and Nyquist one line or none, and packed code names and serving asides into the same lines as each new idea. The remakes 0a v2 (12:40) and 0b v2 (17:57) were followed without help. The pattern:
  - **Toy before real before code.** Each prerequisite, the first time an episode uses it, gets a scene of its own with tiny numbers the viewer can check by eye (an 8-entry 2-D table instead of 2,048 × 512; 8 samples and a 2-tap window at stride 2), labelled 玩具例子 / toy on screen, asserted in a `toy.py` like any other number. Then the same step with the running example's real numbers, then the real source. A toy is not an analogy: it is the real operation at a size you can see.
  - **One new thing per line.** A line introduces a concept, *or* names a code identifier, *or* makes a serving remark, not two of these at once.
  - **Serving asides move to the end.** How the mechanism is used in serving (which path skips it, its cost per request) gets its own scene after the mechanism is understood, not interleaved with it.
  - **Length follows.** Prerequisite scenes may make a part much longer; that is fine. A new part is needed only when a second mechanism appears.
  - **When a learner says "too hard", diagnose before rebuilding.** Measure the pace (words per minute) and list every term the script uses but never taught; in this case the list, not the pace, was the problem.
  - **Test the script before animating.** Give the learner a readable bilingual draft of the script (`script_draft.md`, scene by scene, toy numbers included) and rebuild only after they say it reads well; it costs minutes, a re-animation costs hours.
- **Few new names per scene.** When a scene introduces so many names that the viewer can't hold them (ep11a kept it to about three), split the scene.
- **Analogies wherever a fitting one exists**, decided by fit, not by guessing what the audience already knows: one audience of engineers mixes deep and shallow backgrounds (robot-course: motor-control engineers, some of whom tune current loops daily and some who don't), and a fitting line costs the strong viewer a few seconds while it carries the weak one. *Fitting* means accurate on the point being taught, with a known place where it stops holding. No fitting analogy → none; teach straight from the running example, never force one, since a wrong picture is worse than no picture. Often fitting: timing and concurrency (ep11a: DMA = posting a letter with a reply envelope, read at the next visit), layering, addressing and protocol roles (CANopen's object dictionary = numbered shelves, `0x607A` the shelf and `:00` the slot; SDO vs PDO = a phone call that waits for an answer vs a newspaper delivered on schedule; EtherCAT SYNC0 = one starting pistol for the whole team). For maths mechanisms (observers, input shapers) draw what it does from a real run's waveforms first (raw differentiated speed beside the observer's; a step with and without shaping) and let the analogy only open it (an input shaper = a second push on a swing, timed to cancel the sway). How many per episode is your judgment.
  - **The analogy opens, the running example teaches.** Say it in one or two lines, then land on the running example's real numbers in the same scene (shelf `0x607A` → the bytes `7A 60 00` in the frame on screen). Never build a scene on the analogy alone, and don't carry it past where it fits; say where it breaks if a viewer would otherwise be misled.
  - **One analogy can carry a whole multi-part topic** when it fits the chain of events, not just one scene: then it becomes a memory hook for the shared picture above. ep06: opening a shop (power steady → till connected → scale zeroed → OPEN sign up) maps one to one onto the four gates, its icons sit on the gate board in every part, and 6c says where it breaks (the OPEN sign stays up after closing for lunch: `hw_ready_state` stays 1 after a disable). Smaller scene analogies can still sit inside it (a letter read two days late, a teacher taking the register before a late student signs in).
- **Guess first**, wherever the viewer can genuinely predict something (ep11a had two plus its "your turn"; ep11c asked one at almost every stop): pose the question on a card, hold (`"pause"` as the 4th element of the line in `script.json` adds 2 s of silence in `tts.py` and `silent_timeline.py`), then answer with the real run. Clear the card fully before the answer's picture fades in.
- **"So far" when a lot has piled up** (told on the framework page; ep11a had one every five or six scenes), a final recap on the same page, then a "your turn" that hands the viewer a *new* real input to work by hand, pauses, and shows the answer and the real run.
- **Unhurried timing.** Lines ≤ 20 words; gaps of 0.6 s; subtitles stay long enough to read both languages (the template `silent_timeline.py` timing). One idea per line.
- **Splitting is your judgment** — decide after reading the episode's code, never from the title alone (robot-course ep11 looked like one episode until `drv_encoder.c` showed six types, different check policies and five measured pitfalls; it became 11a–11d). Earlier splits for reference: ep01's nine stops became 1b and 1c; ep11's parallel protocols got their own part (11b); its measured pitfalls got theirs (11c). Signs a part is too dense, besides names: many timestamps for the viewer to hold, detours that leave the main line before it is finished, or more than one mechanism (the first ep06b held call order, a one-tick delay, a lock-free handover, interrupt priorities and a stopwatch; the first ep06a had six stops, two what-ifs and about twelve timestamps; both were remade as 6a–6e, one mechanism each, around one shared picture). More parts alone do not fix a missing backbone; give the parts the shared picture too. Show the user the stop list and the split before producing anything. Keep episode numbers stable; parts are `NNa/NNb/NNc`. A course plan may carry a pre-reading estimate (robot-course `plan.py` `PARTS`), marked as an estimate.
- **One way to split a dense topic** (how ep11 was done): part A = the main path with one example, done thoroughly; part B = the variants, each shown only as its *difference* from part A, stop by stop; optionally part C = what goes wrong (checks, error paths, pitfalls from real runs), each pitfall guess-first, only when those failures teach something the main path doesn't. Part B and C reuse part A's stop strip.

## Video-first courses: the video is the whole course

When a course drops the lab and the atlas (SKILL.md, "Video-first courses"; robot-course since 2026-10-13), the video and its 课件 take over their jobs. Density doesn't change: one mechanism and one running example per video. Extra material makes **more parts**, not more mechanisms per video (prerequisites taught concept-first may still make a part longer, see "Concept first" above). Use the options below when they help this topic, not as a checklist.

| The lab / map used to give | Now carried by |
|---|---|
| Many real-run cases (a table of faults, a sweep of loads) | Optionally a **case-tour part** when several cases are each worth seeing: pick the telling ones, each guess-first then the real run, reusing part A's stop strip. The full table of measured values goes into the 课件. |
| Where the code lives, how modules connect | A **"you are here" strip** on every scene with code: the layer / module and the file, alongside the call-stack breadcrumb. Optionally a **section-recap part** at the end of a section, when its pieces only make sense together: the modules and call chains taught so far on one picture. |
| Predict-then-verify questions | **More guess-first pauses** than a lab-backed course would need, each answered by a real run; the 课件's practice page holds the rest. |
| Trying it yourself | **"Your turn"** ends with the exact repro command from the episode's `data/runs.sh` and what the learner should see. |

Only real runs, as before: every number on screen comes from the harness; anything worked out from the code is labelled as such. A `data.py` per episode runs the harness, checks every number the subtitles state (the build fails if one no longer holds) and writes `epNN_data.js` (`const D`, plus the code excerpts it cuts by line range); `build.py` includes every `*_data.js` before `scenes.js`. Reference: robot111 `episodes/ep02-one-cable-ring/data.py`. Keep the guess-first and practice questions (with answers and the source line or run they rest on) in the 课件. They also seed a later AI voice dialogue, where the learner explains the episode back.

## 3Blue1Brown style, concretely

Visual
- **Dark canvas, few elements, lots of space.** One idea on screen at a time; clear the previous picture (fade it out) before the next one comes in. Never more than ~3 things moving at once. The framework page ("Conclusion first" above) is dense on purpose: it is built up part by part and nothing on it moves.
- **Colour means something, consistently, for the whole episode.** Pick a colour per concept in the outline (e.g. stiffness coral, damping violet, targets gold, measurements sky) and use it for the symbol in formulas, the arrow in the picture, the curve in the graph and the word in the chip. Write the legend as a comment at the top of `scenes.js`.
- **Formulas are built, not shown.** Introduce a symbol only after the picture it names is on screen; fade terms in one at a time (`eq` with per-part alpha) or `wipe` them in left→right; point at parts with `brace`; dim terms that are switched off instead of removing them, so positions stay put.
- **Everything moves continuously.** Values sweep rather than jump (a dot sliding along a graph line while the arm moves, a counter ticking with a gear). Use `eio`/`eo` easing; avoid hard cuts inside a scene.
- **Show, then name, then formalise.** Picture/analogy → plain-language name → symbol → formula → concrete numbers plugged in.
- **Real numbers on screen.** After the general formula, always plug in one worked example (N = 10, Kp = 20 → 0.2) and show the arithmetic.
- **Code last, verbatim, mapped back.** When the episode reads real source, show the real lines (with file and line numbers, see "Code on screen is the real code" above) in `codeBox`, highlight each line as the narration names it, and colour it with the same concept colours as the formula. Shorten by choosing fewer lines, never by rewriting them.

Narration (script.json)
- **Talk like a senior engineer to a peer.** "you", "we", short sentences, one idea per line. ≤ 20 words per line so it fits two subtitle rows. The Chinese line wraps too (`wrapZh` in `tail.html`: at 1700 px, preferring a break after ，。：；), but keep it about one row: a third subtitle row covers the scene.
- **Every identifier the narration names gets its role in a few words**, the first time it comes up and again when it returns later (see "Every name the video points at says what it is" above); a field term gets the same treatment; the field's basics get one line at most when the learners know the field, and a concept-first scene when they don't (see "Concept first" above).
- **A fitting analogy may open a hard idea** (see "Analogies" above), then land on the running example's numbers.
- **Ask, pause, answer.** Pose the question the viewer should be asking ("so why not just make Kp huge?"), give it a beat, then answer. A few per episode.
- **A failure scene is optional.** When the outline has a "what breaks without it" moment, it gets its own scene: either as the opening problem, before the mechanism, or after the main path. Never put it in the middle of the path. Most episodes need none (see "Logic first, without jumps" above).
- **Conclusion first, recap mid-way and at the end.** The whole mechanism in one or two sentences right after the intro; one "so far:" scene around the middle and one recap scene at the end, both told on the framework page; then a "your turn".
- No jargon walls, no "obviously/simply/just", no unexplained acronyms.

## Fact-check the script against the source (before animating)
Every claim in `script.json` about the codebase gets checked against the real source before any scene is drawn: function names and call order (grep each one and read the call site, not just the definition), which interrupt or thread runs it and at what priority, constants and units (read the `#define` and the setter that converts), what a return value means and whether the caller even reads it. Every gloss of a name too ("JDR1, the injected-conversion register"): read its declaration and where it is written, so the gloss says what the code makes it, not what the name suggests. Numbers on screen come from a real run when the course has a runnable target. When a measured value changes from run to run (host timings of code compiled on a laptop), quote only what holds every run ("well under a microsecond", "the last value hides a slowest tick several times longer"), show the run's own numbers on screen labelled with where they come from, and let the data script check the stated property rather than a fixed number. Then re-check anything an earlier episode, the plan or the project map says about the same path: when they disagree, the source wins, and the other place gets fixed in the same pass. On robot-course ep36 this pass caught four wrong claims (where an edge was detected, which interrupt receives CAN frames, a PWM centre value, a current sign), two of them already published in episode 1's map.

## script.json
Array of scenes `{id, title, zh, lines: [[english, chinese, spoken?, hold?, source?], …]}`; a scene may also carry `visual` (what the picture does, for review). `title`/`zh` show as the chapter heading in the video and become chapter names (`zh` in Chinese mode, `title` in English mode). One line = one subtitle = one **beat**. The optional third element is what the TTS says when it should differ from the subtitle ("theta star" for "θ*", "M I T", "Map Reduce") — always give one when the subtitle has symbols, code identifiers or Chinese (in a Chinese-narrated course it is a Chinese spoken form, and English names may stay as they are). The fourth holds the picture after the line: `"pause"` (2 s to guess before the answer) or a number of seconds. The fifth is a source note for fact-checking (§section, figure, `file:line`); it is never read or shown.
- Changing any line re-synthesizes only that line (hash cache), but shifts every later time → re-run tts, build, record, sync.

## tts.py (Gemini TTS, or MiniMax TTS)
Model `gemini-3.8-flash-tts` (override `GEMINI_TTS_MODEL`), voice `Sulafat` — warm (override `GEMINI_VOICE`; `Achird` friendly, `Charon` informative, `Kore` firm). Style text in `GEMINI_TTS_STYLE` (default "a clear, confident senior engineer explaining to a fellow engineer…"). All three can go in `~/.config/course-studio/.env` (defaults for every course) or a course-root `.env` (just this course).
- The style is sent as a `### DIRECTOR'S NOTES` header before `### TRANSCRIPT`. A plain "Say this like…:" prefix gets read aloud by this model, and `systemInstruction` is rejected — don't change that.
- Returns 24 kHz mono WAV; 4 lines are synthesized in parallel with retries on 429/5xx. A clip longer than `3 s + 0.75 s/word` is regenerated (up to 3 tries) and then flagged with a WARNING — listen to it and reword the line (mixed-language text is the usual cause: keep `spoken` pure English).
- **Listen-back check.** The TTS model sometimes reads the director's notes aloud mid-line ("…to a fellow engineer, natural, brisk but unhurried pace…") and still passes the length limit. So every new clip is transcribed by the "ears" in `asr.py` and regenerated on leaked style words or a clip far too long/short; the last two tries send the bare line without notes. `CHECK_PROVIDER` picks the ears: `auto` (default: Gemini `GEMINI_CHECK_MODEL`, falling back to MiniMax ASR `asr-1.0` when Gemini has no key, or runs out of credit — HTTP 402 — or daily quota in the middle of a run), `both` (two independent ears: both right passes, both wrong re-voices, a disagreement passes but is listed in `check_disagree.txt` for a human), `gemini`, `minimax`, `off`. A clip that passed gets an `audio/*.ok` marker; cached clips without one are checked once on the next run. The check costs one request per line on the text model.
- **Free-tier quota is 100 requests per model per day**; retries and checks count. A 110-line episode with retries can need two days on a free key — finish the rest the next day (the cache keeps finished lines).
- **`TTS_PROVIDER=minimax`** voices the lines with MiniMax `speech-2.8-turbo` instead (`MINIMAX_API_KEY`; `MINIMAX_BASE_URL` defaults to the China site `https://api.minimax.cn/v1`, the international site is `https://api.minimax.io/v1`; `MINIMAX_VOICE`, default `English_expressive_narrator`, other system voices via the platform's voice list; `MINIMAX_SPEED`). Billed per character with no daily request cap, 32 kHz mono WAV, about 1.3 s per line; no director's notes are sent, so there is nothing to leak, and the listen-back check needs no Gemini key: with only `MINIMAX_API_KEY` the ears are MiniMax ASR (`asr-1.0`, same key; `CHECK_PROVIDER=off` to skip). Clips are cached per provider, model and voice: switching providers re-voices every line, and a course should keep one voice across episodes (first used on robot-course ep12b, 2026-10-30, as a comparison against the Gemini-voiced episodes).
- The listen-back check spells digits out before comparing (`39,321` ↔ "thirty-nine thousand three twenty-one"), so a spoken form with numbers in words no longer trips the length band.
- **Chinese narration** (`"narration": "zh"` in the episode's `episode.json`, written by `new_episode.py --narration zh`; or `NARRATION=zh` in the environment or a course `.env`): the voice says the Chinese line (or its spoken form) with MiniMax unless `TTS_PROVIDER` says otherwise, voice `MINIMAX_VOICE_ZH` (default `Chinese (Mandarin)_Gentleman`), `language_boost` Chinese; the listen-back check transcribes Chinese and compares by similarity (≥ 0.75). It is lenient: check names and numbers by hand (video-paper.md, "Checking Chinese narration"). `python3 tts.py --voices A B C` writes the first line in each voice to `voices/` for an audition.
- Trims silence, lays lines out with LEAD 0.9 s before a scene, GAP 0.6 s between lines, TAIL 1.6 s after; writes `narration.wav`, `narration.mp3` (for the preview player) and `timeline.json`: `{total, scenes: [{id, title, zh, start, dur, beats: [{text, zh, start, dur, speech}]}]}` (beat start is relative to the scene; `speech` is the voice alone, `dur` adds the hold).

## silent_timeline.py
Same outputs as `tts.py` without any API: each line lasts `max(3.2 s, words/2.3, hanzi/4.2) + 0.6 s` plus its hold; with Chinese narration it lasts as long as the Chinese voice would take (≈ 6 speaking units/s, measured on MiniMax's Gentleman voice), so voicing it later moves the timings only a little. Use it to show the user the look first, or for a subtitles-only video. Scenes written against it keep working after switching to `tts.py`, because they time off `b[i]`.

## scenes.js
`SCN[id] = (lt, b, d) => { … }` per scene: `lt` seconds into the scene, `b[i]` start of beat i, `d` scene duration. Pure function of time — no state, no `Date.now()` — so seeking and frame-by-frame recording are exact.
- Time everything off beats: `const a = eo(ramp(lt, b[1], b[1] + .6))` fades in exactly when line 2 starts. `knots(t, [[t0,v0],[t1,v1],…])` for multi-stage motion. Physical motion should be a closed-form function of time (e.g. `stepResp(t, ω, ζ)` for a damped settle), not a simulation loop.
- Engine (head.html): canvas 1920×1080; colors `C.{bg,ink,dim,faint,line,panel,panel2,sky,coral,gold,mint,red,violet}`; fonts `F.{disp,sans,mono,zh}`; easing `ramp, eo, eio, eback, lerp, knots, rnd(i)`.
  - general: `text, rr, glow, dot, packet(a,b,p,color,{bend,label}), burst, cross, check, ringArc, pulse, tag, chip, panel, arrow, fileIcon, cylinder, lockIcon, server, user, hexagon, nodeCircle, wrapLines`
  - 3b1b maths: `eq(parts, cx, y, size, {left, glow, alpha})` with parts `[str, color, alpha?, sub?]` (italic serif; `sub` draws a subscript); `wipe(p, x, y, w, h, fn)`; `brace(x1, x2, y, label, color, a, dir)`; `axes(x, y0, w, h, {xl, yl, full, both})`; `plot(fn, x, y0, w, k, prog, color)`; `stepResp`; `DEG`
  - mechanics: `arm(px, py, L, θ, {ghost, color, mass, lw})` (θ CCW from +x), `tip`, `arcArrow(px, py, r, a0, a1, color)`, `springArc(px, py, r, a0, a1, color)`, `gear(x, y, r, teeth, rot, color, {mark, spokes})`
  - text blocks: `codeBox(x, y, w, title, lines, {hl(i), mark(i), base, lh, size, file, from, to})` (source lines in `F.code`, a ligature-free font; `lh` = line height, e.g. 30 to fit 14 lines), `label2(en, zh, x, y)`
- tail.html draws the chrome: chapter number + title top-left (scenes 1…n-2), progress ticks top-right, subtitles bottom. Keep scene content between y≈160 and y≈840.
- `build.py` collects every Chinese character in scenes.js into `EXTRA_ZH` so the font subset loads them — nothing to maintain by hand.
- Add episode-specific helpers at the top of scenes.js (e.g. the episode's main formula as an `eq` parts builder); promote them to `head.html` in the skill's template only if they're generic.
- Reference episodes for this style: `~/Documents/ChatGPT/robot-course/episodes/ep02-sil/` (real SIL waveforms from `data/*.csv`, code boxes) and `ep06a-four-gates/` … `ep06e-who-interrupts/` (one topic in five parts around one shared picture: `gates.part.js` draws the gate board full size and as the corner copy; picture-left / code-right scenes; `srcView` panes cut by `make_src.py`; real runs and call traces via `make_data.py`, which checks every number the subtitles quote; `scenes.js` is concatenated from `data.js`, `src.js`, `scenes.head.js`, `kit.part.js`, `helpers.part.js`, `gates.part.js` and `scenes.body.js` by `build.sh`).

## Checking before recording
`node frames.mjs [sceneId …]` renders a frame near the end of every beat and tiles them 2×2 into `frames/sheet-*.jpg`; read the sheets and fix overlaps, off-canvas text, subtitle collisions and titles long enough to hit the progress ticks (keep a chapter `title` under ~32 characters). `node moments.mjs [sceneId …]` then tiles the switches between lines (0.25 s before and 0.15 s after each line start), where crossfades and half-gone cards hide; `node moments.mjs scene:line:+0.1` renders one exact moment. Recording a 10-minute episode takes ~8 minutes (≈ 40 frames/s); do it last, then pull 3–4 frames from the mp4 to confirm.

## Slides (课件): every video gets one
After recording, `node slides.mjs` (≈ 20 s) turns the video into a handout: it renders a frame near the end of every beat with `?nosubs` (no burned-in subtitles; the narration goes beside the picture as text, Chinese and English), and merges consecutive beats of one scene into one slide when the picture barely changed (`--min-diff`, default 1.2) or only gained things — the 3b1b build-up, where a term, a box or a curve appears — so each slide shows the finished picture with all the lines that built it (capped by `--max-lines`, default 6; `--keep-builds` keeps every build step). A highlight moving, a box fading out or a new layout starts a new slide. robot-course ep02: 89 beats → 40 slides.
- `slides.html` (from `slides_page.html`, Bento, 中 / EN): chapters as a sticky chip row, each slide a tile with the screenshot (click to enlarge) and its narration, a `▶ m:ss` link that opens the course home at `#epNN@seconds` and plays the video from there (only when served by the site).
- `slides.pdf`: A4 landscape, one slide per page, notes in both languages — for printing or reading offline. `--no-pdf` skips it. The page has a fixed height, so the picture shrinks to make room for the notes. If notes still overflow, `slides.mjs` prints `⚠ slides.pdf: notes clipped on slide …`: don't ship that PDF. Episodes made before 2026-10-24 clipped any slide with 4+ lines: copy `slides.mjs` and the `@media print` block of `slides_page.html` from the template, then rerun.
- Read the contact sheet before shipping: `cd slides && ffmpeg -framerate 1 -i %03d.jpg -vf "scale=480:-1,tile=5x8" -frames:v 1 ../sheet.jpg`. Too many near-repeats → raise `--min-diff`; a slide missing something that was on screen briefly → lower it.
- **Two pages close the 课件** (every course; essential in a video-first one). **Code index**: every code pane in the video, in order of appearance: file, line range, function, the chapter and slide it is on, and the video times. `slides.mjs` finds them by playing the video through every 0.25 s and listening to `codeShown({file, a, b, fn?, key?})`. `codeBox` calls it with its title, or with `{file, from, to}` when given those options. A helper that draws real source calls it itself when its pane is more than half visible (robot-course ep11a `srcView`). Only identifiers are kept from `fn`, because prose labels exist in one language only. **Practice**: written by hand in `practice.json` as `{questions: [{q, a, why: [中文, English], scene?, src?: ['file.c:647–650'], run?, reasoned?}]}`. Use `scene` for a question the video asks (the page links to that moment). Leave it out for a new question. Write 2–3 new questions beyond the video's. Each `why` quotes the real run (`run` = its command, also added to `data/runs.sh`) or the source lines. Set `reasoned: true` only when no run backs the answer, and the page then labels it 按代码推演. Answers fold away on the page and print open in the PDF. Template: `template/episode/slides.mjs` + `slides_page.html`. An older episode gets them by copying both, plus `codeShown` from the template's `head.html`. Reference: robot-course `episodes/ep11a-one-frame/practice.json`.
- Re-run it whenever the video is re-rendered (it reads `index.html` and `timeline.json`, so it always matches the current video).
- Episodes made before this existed: copy `slides.mjs` and `slides_page.html` from `template/episode/` (fill the `__EP_…__` / `__COURSE_…__` placeholders in the page by hand), and add the `NOSUBS` guard from the template's `tail.html` to the episode's `tail.html`, then `build.py`.
